# ERA5 下载服务器部署指南

> 配套代码：`src/tcc/download_workers.py`　配置：`configs/download.yaml`　部署文件：`deploy/`
>
> **本流程不创建任何专用用户**，直接用 root 部署。适合按量付费的短期服务器。

---

## 〇、先做减法，再谈部署

**部署之前请务必确认下载量已经压下来了。** 原始写法（逐小时 + 大域）是 **196 GB / 540 个请求**；优化后是 **8.2 GB**。

| 优化点 | 效果 |
| --- | --- |
| 三类数据全部改用**服务端派生日统计数据集** | 24× |
| `tmax` 分组只下研究区 `[34,110,28,122]` | 再降 38× |
| `month` 零填充 `'05'`（ERA5-Land 只认零填充） | 修掉一个必现的请求错误 |
| `day` 按 `calendar.monthrange` 生成（6 月只有 30 天） | 避免送不存在的日期 |

```bash
uv run python src/tcc/download_workers.py --config configs/download.yaml --dry-run
# 任务总数: 540  预估体积: 8.18 GB（未压缩）
```

## 一、目录约定

整套流程只用到这四个路径，后文命令全部基于它们：

| 路径 | 用途 |
| --- | --- |
| `/opt/tcc` | 代码（`git clone` 到这里） |
| `/opt/tcc/.venv` | 最小 Python 环境（只装 5 个包） |
| `/opt/tcc/.cdsapirc` | CDS API 凭据 |
| `/srv/tcc-data` | **数据 + 断点续传状态 + 日志**（全部产物集中在这里，方便快照和取回） |

> 想换路径也行，但 `deploy/tcc-download.service` 里是硬编码的，改了要同步改 unit。

## 二、部署流程（6 步）

### Step 1｜开服务器

- 地域：**香港 / 新加坡**（不要选国内 —— 访问 CDS 和 Google Cloud 都不通）
- 配置：**2 核 2 GB / 40 GB SSD** 起步
- 镜像：Ubuntu 22.04 或 24.04
- 安全组：放行 22（SSH）即可，**不用开 80/443**（不需要备案）

### Step 2｜装系统依赖和 uv

```bash
apt update && apt install -y curl git

curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"      # 建议写进 ~/.bashrc
uv --version
```

> uv 会自己管理 Python 版本，**不依赖系统自带的 python3**。

### Step 3｜拉代码

```bash
mkdir -p /opt/tcc
git clone <你的仓库地址> /opt/tcc
cd /opt/tcc
```

> `git clone` 到一个**空目录**是允许的，所以先 `mkdir` 再 clone 没问题。

### Step 4｜建最小环境（关键：不要 `uv sync`）

```bash
uv venv /opt/tcc/.venv --python 3.13

uv pip install --python /opt/tcc/.venv \
    "cdsapi>=0.7.7" "cdsswarm>=0.3.0" "pyyaml>=6.0" \
    "xarray>=2026.7.0" "netcdf4>=1.7.4"
```

**⚠️ 为什么不能 `uv sync`**：那会把 `torch`、`cartopy`、`metpy`、`earthkit` 等一起装上。
**实测对比：最小环境 163 MB，完整环境 6.8 GB —— 差 42 倍**，而下载任务一个都用不到那些包。

**⚠️ 为什么用"按路径跑脚本"而不是 `python -m tcc.download_workers`**：
后者要求 `tcc` 包已经安装进 venv，而 `uv pip install -e .` 会把全部主依赖拖进来。
`download_workers.py` 是**自包含**的（不 import 包内其他模块），所以直接给路径就能跑：

```bash
/opt/tcc/.venv/bin/python /opt/tcc/src/tcc/download_workers.py --help
```

### Step 5｜配置 CDS 凭据

```bash
cat > /opt/tcc/.cdsapirc <<'EOF'
url: https://cds.climate.copernicus.eu/api
key: <你的 CDS API Key>
EOF
chmod 600 /opt/tcc/.cdsapirc
```

**⚠️ 这一步有个坑（我踩过）**：cdsapi 的凭据查找顺序是 `$CDSAPI_RC` → `~/.cdsapirc`。
systemd unit 里设了 `CDSAPI_RC`，但**你在 shell 里手动跑脚本时它不生效**，
于是 cdsapi 会去找 `/root/.cdsapirc` 并报
`Missing/incomplete configuration file`。

**最省事的做法是把凭据同时放到默认位置**，这样手动跑和 systemd 跑都不会出问题：

```bash
cp /opt/tcc/.cdsapirc /root/.cdsapirc && chmod 600 /root/.cdsapirc
```

或者更干净的方式——在 `configs/download.yaml` 里显式指定（脚本会在启动时做凭据预检）：

```yaml
cdsapirc: /opt/tcc/.cdsapirc
```

> 脚本现在会在**提交任何请求之前**先预检凭据：文件不存在或内容不完整就立刻退出（退出码 2）
> 并打印三种修法，而不是白提几百个请求、白等 30 轮退避。

> ⚠️ 凭据**绝对不要提交进 git**。`.gitignore` 里已经加了 `.cdsapirc`。

### Step 6｜冒烟测试（别跳过）

先跑一个小范围，确认三个数据集都能正常下载并打开：

```bash
mkdir -p /srv/tcc-data

# 只改年份和月份，其余不动
cp configs/download.yaml /tmp/smoke.yaml
sed -i 's/^years: .*/years: [2024, 2024]/; s/^months: .*/months: [7]/' /tmp/smoke.yaml

TCC_DATA_DIR=/srv/tcc-data \
  /opt/tcc/.venv/bin/python /opt/tcc/src/tcc/download_workers.py --config /tmp/smoke.yaml
```

跑完（约几十 MB）后逐个打开验证：

```bash
/opt/tcc/.venv/bin/python -c "
import xarray as xr, glob
for f in sorted(glob.glob('/srv/tcc-data/raw/*/*.nc')):
    with xr.open_dataset(f) as ds:
        print(f.split('/')[-1], dict(ds.sizes), list(ds.data_vars))
"
```

确认三个分组都有文件、维度里 `time` 是天数（不是 24 的倍数）、变量名正确，再进入下一步。

### Step 7｜装 systemd 并启动

**推荐用安装脚本**——它会自动探测「代码在哪、venv 在哪」，据此生成 unit，
并在安装前跑一次 `--dry-run` 自检，**把路径写错导致的 203/EXEC 挡在安装阶段**：

```bash
sudo bash /opt/tcc/deploy/install.sh
```

想先看看它会写什么（不需要 root，也不会改系统）：

```bash
bash /opt/tcc/deploy/install.sh --print-unit
```

如果你更想手工来，静态模板在 `deploy/tcc-download.{service,timer}`，
但**必须把里面的 `/opt/tcc` 和 `/srv/tcc-data` 改成你的实际路径**：

```bash
cp /opt/tcc/deploy/tcc-download.{service,timer} /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now tcc-download.timer
```

**验证**：

```bash
journalctl -u tcc-download -f
systemctl list-timers tcc-download.timer
```

**两个 unit 的分工**：

- `tcc-download.service`（`Type=oneshot`）：实际执行下载，内部有 30 轮退避重试；
- `tcc-download.timer`：每 30 分钟兜底触发一次。脚本是**幂等**的——已完成的文件跳过、
  未完成的继续，**不会重复下载**；上一次没跑完时 systemd 不会并发启动第二个实例。

> 为什么不用 `Type=simple` + `Restart=always`？因为 `Restart=` 与 `Type=oneshot`
> 组合在 systemd 里语义含糊，**timer + 幂等脚本**是更标准、更好排障的做法。

卸载：`sudo bash /opt/tcc/deploy/install.sh --uninstall`（数据目录不会被删）

## 三、断点续传靠什么保证（三层）

`cdsswarm` 0.3.0 已经内置，脚本只是把它们显式打开：

| 层 | 机制 | 保障什么 |
| --- | --- | --- |
| 1 | `skip_existing=True` | 进程重启不重下已有文件 |
| 2 | **`reuse_jobs=True`** | **复用 CDS 上已提交/已完成的 job，不重新排队** |
| 3 | 会话状态持久化 | 每个任务的 `cds_request_id` 写在 `$XDG_CACHE_HOME/cdsswarm/sessions/*.json`，进程被杀可续 |

**第 2 层是真正的护身符**：CDS 排队动辄 4—15 小时，如果掉线就要重新排队，那才是灾难。
只要请求参数一个字都不变，重跑就是取缓存。

```bash
# ⚠️ 千万不要改这些字段，改了等于换了个请求，要重新排队：
#    dataset / variable / year / month / day / area / daily_statistic / time_zone / frequency
```

脚本外层还加了两层保险：

- **轮次级重试**：`cdsswarm` 内部重试 10 次；整轮跑完仍有失败，外层按
  60s → 120s → … → 30min 退避再来，最多 30 轮；
- **坏文件校验清理**：CDS 出错时会把 **HTML 错误页写成 `.nc`**，脚本用 magic bytes +
  xarray 双重校验，不过的文件自动删除，下一轮重下。

查看续传状态：

```bash
ls -la /srv/tcc-data/.cache/cdsswarm/sessions/
/opt/tcc/.venv/bin/python -c "
import json, glob
from collections import Counter
for f in glob.glob('/srv/tcc-data/.cache/cdsswarm/sessions/*.json'):
    ts = json.load(open(f)).get('tasks', {})
    print(f.split('/')[-1][:12], Counter(t['status'] for t in ts.values()))
"
```

## 四、要不要用 Docker？——**这个任务不需要**

| 维度 | systemd + uv | Docker |
| --- | --- | --- |
| 配置复杂度 | 两个 unit 文件 | Dockerfile + compose + volume + 镜像构建 |
| 数据持久化 | 直接写 `/srv/tcc-data` | **仍需**挂 volume，没省事 |
| 断点续传状态 | 一个环境变量搞定 | **必须额外挂一个卷**，否则容器重建就丢状态、重新排队 |
| 内存开销 | 0 | dockerd 常驻约 100—200 MB（2 GB 机器上不划算） |
| 排障 | `journalctl -u` | 多一层容器网络/挂载要查 |

**结论：用 systemd + uv。** 这就是个"跑 Python 脚本往磁盘写文件"的任务，
容器化没带来任何实质收益，反而多了一个丢状态的风险点。

只有两种情况才值得上 Docker：① 要和别的服务一起用 compose 编排；② 想统一成一个
镜像到处跑。文件已经写好了（`deploy/Dockerfile`、`deploy/docker-compose.yml`）：

```bash
cd /opt/tcc/deploy
TCC_HOST_DATA=/srv/tcc-data TCC_HOST_CACHE=/srv/tcc-cache \
  docker compose up -d --build
docker compose logs -f
```

## 五、取回数据 & 分发给队友

下载完成后，脚本会自动生成校验和清单 `/srv/tcc-data/CHECKSUMS.sha256`。

```bash
# 本地拉取（rsync 支持断点续传）
rsync -avhP --partial root@<服务器IP>:/srv/tcc-data/raw/ ./data/raw/
rsync -avhP root@<服务器IP>:/srv/tcc-data/CHECKSUMS.sha256 ./data/

# 校验（所有人都要跑，确保用的是同一份字节）
cd data && sha256sum -c CHECKSUMS.sha256
```

> ⚠️ **ERA5 版本会漂移**：ECMWF 会不定期重跑 ERA5 发布新版本。所以必须
> **一个人下载、其他人复用**，并用 sha256 对齐。不要各自下载后混用。

## 六、故障排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 请求报 `month` 无效 | ERA5-Land 只认零填充 `'05'` | 已修 |
| 请求报 6 月 31 日无效 | `day` 硬编码 1—31 | 已修 |
| 一直 `Accepted / Queued` | CDS 排队（论坛实测 Running 80 / Queued 5832） | 正常，等着；**别改请求参数** |
| 下下来的 `.nc` 打不开 | CDS 把 HTML 错误页写成了文件 | 脚本自动删除并重下；也可 `--verify-only` 手工清点 |
| 重启后又要重新排队 | `XDG_CACHE_HOME` 没指到持久盘 | 检查 unit 里的 `Environment=XDG_CACHE_HOME=` |
| 磁盘满 | 没做 area 子集 | `du -sh /srv/tcc-data/raw`；确认配置里 `area` 生效 |
| 进程被 OOM 杀掉 | `workers` 开太大 | 2 GB 内存机器 `workers` ≤ 6 |
| `systemctl status` 报 203/EXEC | **unit 里的 ExecStart 路径和实际不符**，或 **ProtectHome 挡住了 venv 解释器** | 见下方「实战记录」第 1 条 |
| 报 `No module named tcc` | 用了 `python -m tcc.download_workers` | 改用按路径执行：`python /opt/tcc/src/tcc/download_workers.py` |
| 报 `Missing/incomplete configuration file: /root/.cdsapirc` | 手动跑时 `CDSAPI_RC` 没生效 | `cp /opt/tcc/.cdsapirc /root/.cdsapirc && chmod 600 /root/.cdsapirc` |
| 大量 `Number queued requests for this dataset is temporarily limited` | **CDS 单账号排队请求数配额** | 降低 `workers`、降低 `max_retries`、拉长轮次间隔；见下方「实战记录」第 2 条 |
| 卡在 `502 Bad Gateway` / `8972 queued` | CDS 服务端过载（非配置问题） | 无解，只能等；脚本会自己退避重试 |
| `systemctl stop` 迟迟不返回 | cdsswarm 要先跑完手上的重试 | 已把 `TimeoutStopSec` 设为 60，超时由 systemd 发 SIGKILL；急用可 `systemctl kill -s SIGKILL` |
| `uv pip install` 说已安装但 `import` 失败 | dist-info 在、包文件缺失（残破安装） | `uv pip install --python /opt/tcc/.venv --reinstall <包名>` |

## 六之二、实战记录：三个真踩过的坑

以下都是实际部署时**真实发生并通过日志定位**的问题，按出现顺序记录。

### 坑 1：`ProtectHome` 挡住了 venv 的解释器（现象是 203/EXEC）

**现象**

```
tcc-download.service: Unable to locate executable '/opt/tcc/.venv/bin/python': No such file or directory
tcc-download.service: Main process exited, code=exited, status=203/EXEC
```

**迷惑点**：`ls -l /opt/tcc/.venv/bin/python` 明明存在。

**根因**：`uv` 建的 venv，`bin/python` 是指向 **uv 托管 Python** 的符号链接：

```
/opt/tcc/.venv/bin/python
   → /root/.local/share/uv/python/cpython-3.13.15-linux-x86_64-gnu/bin/python3.13
```

而 unit 里有 `ProtectHome=true`，它会把 `/home`、`/root`、`/run/user` **整个隐藏掉**。
systemd 解析符号链接时看不到目标，于是报"文件不存在"——但文件其实好端端在磁盘上。

**定位方法**

```bash
readlink -f /opt/tcc/.venv/bin/python     # 看链接最终指向哪
```

**修法**：`deploy/install.sh` 现在会检查**解释器解析后的真实路径**，
只要落在 `/home`、`/root`、`/run/user` 下就自动省略 `ProtectHome`，
并在 unit 里写明原因。生成的注释长这样：

```ini
# ProtectHome 已省略：解释器 /root/.local/share/uv/python/... 位于 /root 下，启用后服务将读不到它
ReadWritePaths=/srv/tcc-data
```

> 想保留 `ProtectHome` 的加固，可以改用 `ProtectHome=read-only`（只读仍可执行），
> 或者把托管 Python 装到系统目录：`UV_PYTHON_INSTALL_DIR=/opt/uv-python uv venv ...`。

### 坑 2：CDS 的"排队请求数"配额

**现象**

```
The job has been rejected
Number queued requests for this dataset is temporarily limited. Please configure your scripts accordingly
```

日志统计：`accepted: 12` 但 `limited: 93`。

**根因**：CDS 对**单个账号、单个数据集**的"排队中请求数"有硬上限（实测约 6 个）。
一次把 540 个任务全丢过去，超出的部分直接被拒。

**更糟的是**：`cdsswarm` 的重试**每次都会创建一个新 job**。
日志里累计出现了 **39 个 job id**，而真正 accepted 的只有 12 个——
重试在放大这个问题。

**三项修法（都已落地）**

| 措施 | 改前 | 改后 | 作用 |
| --- | --- | --- | --- |
| `workers` | 6 | **3** | 保持在配额以内 |
| `max_retries` | 10 | **2** | 重试不再堆积废 job |
| `year_batch` | — | **5** | 请求数 540 → 108，减少撞配额的轮次 |
| 轮次退避 | 60s 起 | **300s 起，上限 1h** | 给队列消化时间 |

> **为什么 `year_batch` 不合并月份**：一个请求只能给一份 `day` 列表，
> 而 6 月没有 31 日。合并月份就得放宽到 `01—30`，会丢掉 5/7/8 月的 31 日。
> 所以只合并年份，月份保持独立。

### 坑 3：`netcdf4` 元数据在、文件不在

**现象**

```bash
uv pip install --python /opt/tcc/.venv netcdf4
# Checked 1 package in 1ms          ← uv 认为已装好
python -c "import netcdf4"          # ModuleNotFoundError
```

**根因**：`site-packages/` 里有 `netcdf4-1.7.4.dist-info` 和 `netcdf4.libs`，
但真正的包文件缺失——一次中断的安装留下的残骸。

**修法**

```bash
uv pip install --python /opt/tcc/.venv --reinstall netcdf4
```

### 附带澄清：断点续传到底靠哪一层

实测发现，用**库 API**（`cdsswarm.download(...)`）时，
`~/.cache/cdsswarm/sessions/*.json` 会话文件是**空的**——那是 CLI 模式的功能。

所以库模式下真正的续传保障是前两层：

1. `skip_existing=True` —— 已下载的文件跳过；
2. **`reuse_jobs=True`** —— 重启后向 CDS 查询参数匹配的已提交 job 并复用，**不重新排队**。

**第 2 层才是关键**，也因此更凸显一条纪律：
**请求参数一旦定下就不要改**（`dataset` / `variable` / `year` / `month` / `day` /
`area` / `daily_statistic` / `time_zone` / `frequency`），改了就等于换了个请求，
之前的排队进度全部作废。

## 七、运维要点

```bash
# 查看状态
systemctl status tcc-download.service
systemctl list-timers tcc-download.timer

# 看进度
find /srv/tcc-data/raw -name "*.nc" | wc -l
du -sh /srv/tcc-data/raw

# 暂停（不删除进度）
systemctl stop tcc-download.timer
systemctl stop tcc-download.service

# 恢复
systemctl start tcc-download.timer
```

**⚠️ 用完记得释放实例（不是关机）**

按量付费实例**关机后云盘继续计费**，只有**释放**才停止。释放前务必：

1. `rsync` 把数据拉回本地，并 `sha256sum -c` 校验通过；
2. `du -sh` 确认体积正常；
3. 再释放。

## 八、配置速查（`configs/download.yaml`）

| 字段 | 说明 | 建议 |
| --- | --- | --- |
| `workers` | 并行 worker 数 | 2 GB 内存机器 ≤ 6 |
| `max_retries` | 单任务重试次数 | 10 |
| `max_rounds` | 外层轮次上限 | 30；跑完仍失败可再手动运行（不重下已完成） |
| `frequency` | `1_hourly` / `3_hourly` / `6_hourly` | **必须 `1_hourly`**：`3_hourly` 会让日最高温产生约 1℃ 误差，而本项目 σ(d) 仅 1.2—1.5℃ |
| `time_zone` | 日界时区 | 固定 `utc+08:00`，与 Tmax 定义一致 |
| `area` | `[北, 西, 南, 东]` | `tmax` 只要研究区；环流/SST 需要大域 |
| `data_dir` | 数据根目录 | 留 `null`，用环境变量 `TCC_DATA_DIR` 指定 |
