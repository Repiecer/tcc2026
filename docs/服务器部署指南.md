## 〇、先做减法，再谈部署

**部署之前请务必确认下载量已经压下来了。** 原始写法（逐小时 + 全球级大域）是 **196 GB、540 个请求**；优化后是 **8.2 GB**。

| 优化点 | 效果 |
| --- | --- |
| 三类数据全部改用**服务端派生日统计数据集** | 24× |
| `tmax` 分组只下研究区 `[34,110,28,122]` | 再降 38× |
| `month` 零填充 `'05'`（ERA5-Land 只认零填充） | 修掉一个必现的请求错误 |

## 一、要不要用 Docker？——**这个任务不需要**

| 维度 | systemd + uv | Docker |
| --- | --- | --- |
| 配置复杂度 | 两个 unit 文件 | Dockerfile + compose + volume + 镜像构建 |
| 环境可复现 | `uv.lock` 已经锁死 | 同样靠 lock |
| 数据持久化 | 直接写 `/srv/tcc-data` | **仍需**挂载 volume，没省事 |
| 断点续传状态 | `XDG_CACHE_HOME` 指到数据盘 | **必须额外挂一个 volume**，否则容器重建就丢状态 |
| 内存开销 | 0 | dockerd 常驻约 100—200 MB（2 GB 小机器上不划算） |
| 排障 | `journalctl -u tcc-download` | 多一层容器网络/挂载要排查 |
| 开机自启 | systemd 原生 | `restart:` 策略 + dockerd 自启 |

**结论：**

- ✅ **推荐用 systemd + uv**——这是一个"跑个 Python 脚本把文件写到磁盘"的任务，容器化没有带来任何实质收益。
- ⚠️ **只有这两种情况才值得上 Docker**：
  1. 你要在同一台机器上和别的服务一起用 compose 编排；
  2. 团队里有人不熟悉 Python 环境，想统一成一个镜像到处跑。

Docker 方案我也写好了（`deploy/Dockerfile` + `deploy/docker-compose.yml`），想用可以直接用，见第四节。

## 二、方案 A：systemd + uv（推荐）

### 1. 服务器准备

```bash
# 香港/新加坡节点，Ubuntu 22.04/24.04，2 核 2 GB / 40 GB 起步
sudo apt update && sudo apt install -y curl git

# 建一个专用低权限用户（家目录放 /home，代码放 /opt，两者分开）
sudo useradd -r -m -d /home/tcc -s /usr/sbin/nologin tcc
sudo mkdir -p /opt/tcc /srv/tcc-data
sudo chown -R tcc:tcc /opt/tcc /srv/tcc-data
```

### 2. 拉代码 + 建最小环境

```bash
# /opt/tcc 是刚建的空目录，git 可以直接 clone 进去
sudo -u tcc git clone <你的仓库> /opt/tcc
cd /opt/tcc

# 装 uv（它会自己管 Python 版本，不依赖系统的 python3）
sudo -u tcc bash -c 'curl -LsSf https://astral.sh/uv/install.sh | sh'

# ⚠️ 不要 `uv sync`！那会把 torch / cartopy / metpy 一起装上（>2 GB）。
#    下载只需要这几个包，用独立的 venv：
sudo -u tcc /home/tcc/.local/bin/uv venv /opt/tcc/.venv --python 3.13
sudo -u tcc /home/tcc/.local/bin/uv pip install --python /opt/tcc/.venv \
    "cdsapi>=0.7.7" "cdsswarm>=0.3.0" "pyyaml>=6.0" \
    "xarray>=2026.7.0" "netcdf4>=1.7.4"
```

> 为什么能这么装？因为 `download_workers.py` **不 import 包内其他模块**，
> 是自包含的，所以最小环境就够跑。

### 3. 配置 CDS 凭据

```bash
sudo -u tcc tee /opt/tcc/.cdsapirc >/dev/null <<'EOF'
url: https://cds.climate.copernicus.eu/api
key: <你的 CDS API Key>
EOF
sudo chmod 600 /opt/tcc/.cdsapirc
sudo chown tcc:tcc /opt/tcc/.cdsapirc
```

systemd unit 里已经用 `Environment=CDSAPI_RC=/opt/tcc/.cdsapirc` 显式指到这里
（cdsapi 的查找顺序是 `$CDSAPI_RC` → `~/.cdsapirc`），这样即使开了
`ProtectHome=true` 也能正常读到凭据。

> ⚠️ 凭据**绝对不要提交进 git**。`.gitignore` 里已经加了 `.cdsapirc`。

### 4. 先跑冒烟测试（重要）

先改一个小范围的配置，确认整条链路通了再全量跑：

```bash
sudo -u tcc cp configs/download.yaml /tmp/smoke.yaml
sudo -u tcc sed -i 's/^years: .*/years: [2024, 2024]/; s/^months: .*/months: [7]/' /tmp/smoke.yaml

sudo -u tcc TCC_DATA_DIR=/srv/tcc-data \
  /opt/tcc/.venv/bin/python -m tcc.download_workers --config /tmp/smoke.yaml
```

跑通后（约几十 MB），**先确认能正常打开再删掉**：

```bash
sudo -u tcc /opt/tcc/.venv/bin/python -c "
import xarray as xr, glob
for f in sorted(glob.glob('/srv/tcc-data/raw/*/*.nc')):
    with xr.open_dataset(f) as ds:
        print(f.split('/')[-1], dict(ds.sizes), list(ds.data_vars))
"
```

### 5. 装 systemd 服务

```bash
sudo cp /opt/tcc/deploy/tcc-download.service /etc/systemd/system/
sudo cp /opt/tcc/deploy/tcc-download.timer   /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now tcc-download.timer
```

**关于两个 unit 的分工**：

- `tcc-download.service`（`Type=oneshot`）：实际执行下载，内部有 30 轮退避重试；
- `tcc-download.timer`：每 30 分钟兜底触发一次。脚本是幂等的——已完成的文件跳过、
  未完成的继续，**不会重复下载**；上一次没跑完时 systemd 不会并发启动第二个实例。

> 为什么不用 `Type=simple` + `Restart=always`？因为 `Restart=` 与 `Type=oneshot` 组合在
> systemd 里语义含糊，** timer + 幂等脚本**是更标准、更好排障的做法。

### 6. 验证部署

```bash
# 立刻手动跑一次
sudo systemctl start tcc-download.service

# 看日志
journalctl -u tcc-download -f

# 看进度（文件数 + 体积）
sudo -u tcc bash -c 'find /srv/tcc-data/raw -name "*.nc" | wc -l; du -sh /srv/tcc-data/raw'

# 看定时器状态
systemctl list-timers tcc-download.timer
```

## 三、断点续传到底靠什么保证（三层）

这是你最关心的部分。**好消息是 `cdsswarm` 0.3.0 已经内置了，你的原代码其实已经用上了默认值。**

| 层 | 机制 | 触发条件 | 保障什么 |
| --- | --- | --- | --- |
| **1. 跳过已完成** | `skip_existing=True` | 目标文件存在 | 进程重启后不重下已有文件 |
| **2. 复用 CDS job** | `reuse_jobs=True` | 请求参数完全一致 | **不重新排队**——CDS 上已提交/已完成的 job 直接取回 |
| **3. 会话状态持久化** | cdsswarm 把每个任务的 `cds_request_id` 写到 `$XDG_CACHE_HOME/cdsswarm/sessions/<hash>.json` | 进程被杀 / 掉线 | 进程重启后能接着上次的 job 继续轮询 |

**第 2 层是真正的护身符**：CDS 排队 4—15 小时，如果掉线后要重新排队，那才是灾难。
只要你的请求参数**一个字都不变**，重跑就是取缓存。

因此：

```bash
# ⚠️ 千万不要改这几个字段，改了就等于换了一个请求，要重新排队：
#    dataset / variable / year / month / day / area / daily_statistic / time_zone / frequency
```

脚本外层还加了两层保险：

- **轮次级重试**：`cdsswarm` 内部重试 `max_retries=10` 次；一整轮跑完仍有失败，
  外层隔 60s → 120s → … → 30min 退避后再来一轮，最多 `max_rounds=30` 轮；
- **坏文件清理**：下载后用 magic bytes + xarray 双重校验（CDS 出错时会把 HTML
  错误页写成 `.nc`），校验不过的文件自动删除，下一轮重下。

查看状态文件：

```bash
ls -la /srv/tcc-data/.cache/cdsswarm/sessions/
python -c "
import json,glob
for f in glob.glob('/srv/tcc-data/.cache/cdsswarm/sessions/*.json'):
    d=json.load(open(f)); ts=d.get('tasks',{})
    from collections import Counter
    print(f.split('/')[-1][:12], Counter(t['status'] for t in ts.values()))
"
```

## 四、方案 B：Docker（可选）

```bash
cd /opt/tcc/deploy
export TCC_HOST_DATA=/srv/tcc-data
export TCC_HOST_CACHE=/srv/tcc-cache
sudo -E docker compose up -d --build
docker compose logs -f
```

**⚠️ 容器方案有一个必须注意的坑**：

`cdsswarm` 的断点续传状态默认在 `~/.cache/cdsswarm/sessions/`。**容器里的 `~` 是临时层，
容器一重建状态就没了，所有请求都要重新排队。** 所以 compose 里**必须**额外挂一个
`/cache` 卷，并把 `XDG_CACHE_HOME` 指过去——`deploy/docker-compose.yml` 已经处理了。

`restart: on-failure` 的选择理由：脚本退出码 `0` = 全部下完（容器保持停止），
`1` = 仍有未完成（容器重启继续）。用 `unless-stopped` 会在下完后无限空转重启。

## 五、把数据取回本地 & 分发给队友

下载完成后，脚本会自动生成校验和清单 `/srv/tcc-data/CHECKSUMS.sha256`。

```bash
# 本地拉取（rsync 支持断点续传）
rsync -avhP --partial \
    tcc@<服务器IP>:/srv/tcc-data/raw/ ./data/raw/
rsync -avhP tcc@<服务器IP>:/srv/tcc-data/CHECKSUMS.sha256 ./data/

# 校验（所有人都要跑这一步，确保用的是同一份字节）
cd data && sha256sum -c CHECKSUMS.sha256
```

> ⚠️ **ERA5 版本会漂移**：ECMWF 会不定期重跑 ERA5发布新版本。所以必须
> **一个人下载、其他人复用**，并用 sha256 对齐。不要各自下载后混用。

前提：服务器上装了 nginx 或直接开 rsync 服务；或者临时用
`python -m http.server`（记得加密码或只用 Tailscale）。

## 六、故障排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 请求报 `month` 无效 | ERA5-Land 只认零填充 `'05'` | 已修，见 `build_tasks()` |
| 请求报 6 月 31 日无效 | `day` 硬编码 1—31 | 已修，用 `calendar.monthrange` |
| 一直 `Accepted / Queued` | CDS 排队（论坛实测 Running 80 / Queued 5832） | 正常，等着；**别改请求参数** |
| 下下来的 `.nc` 打不开 | CDS 把 HTML 错误页写成了文件 | 脚本会自动删除并在下一轮重下；也可 `--verify-only` 手工清点 |
| 重启后又要重新排队 | `XDG_CACHE_HOME` 没指到持久盘 | 检查 unit 里的 `Environment=XDG_CACHE_HOME=` |
| 磁盘满 | 没做 area 子集 | `du -sh /srv/tcc-data/raw`；确认配置里 `area` 生效 |
| 进程被 OOM 杀掉 | `workers` 开太大 | 2 GB 内存的机器 `workers` 不要超过 6，可在配置里调小 |
| systemd 起不来 | `ProtectHome=true` 挡住了 `.cdsapirc` | 把 `.cdsapirc` 放到 `/opt/tcc/`（不是 `/root`）或改用环境变量 |

看完整日志：

```bash
journalctl -u tcc-download --since "1 hour ago" --no-pager
tail -f /srv/tcc-data/logs/download.log
```

## 七、运维要点

```bash
# 查看服务/定时器
systemctl status tcc-download.service
systemctl list-timers tcc-download.timer

# 暂停（不删除进度）
sudo systemctl stop tcc-download.timer
sudo systemctl stop tcc-download.service

# 恢复
sudo systemctl start tcc-download.timer
```

**⚠️ 用完记得释放实例（不是关机）**

按量付费实例关机后**云盘继续计费**，只有**释放**才停止。释放前务必：

1. 确认数据已用 rsync 拉回本地并通过 sha256 校验；
2. `du -sh` 确认体积正常；
3. 再释放。

## 八、配置速查（`configs/download.yaml`）

| 字段 | 说明 | 调优建议 |
| --- | --- | --- |
| `workers` | 并行 worker 数 | 2 GB 内存机器 ≤ 6，别贪多 |
| `max_retries` | 单任务重试次数 | 10 起步 |
| `max_rounds` | 外层轮次上限 | 30；跑完仍失败可再手动运行（不重下已完成） |
| `frequency` | `1_hourly` / `3_hourly` / `6_hourly` | **必须 `1_hourly`**：`3_hourly` 会让日最高温产生约 1℃ 误差，而本项目 σ(d) 仅 1.2—1.5℃ |
| `time_zone` | 日界时区 | 固定 `utc+08:00`，与 Tmax 定义一致 |
| `area` | `[北, 西, 南, 东]` | `tmax` 只要研究区；环流/SST 需要大域 |
| `data_dir` | 数据根目录 | 留 `null`，用环境变量 `TCC_DATA_DIR` 指定 |
